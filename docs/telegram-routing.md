# 多 Telegram Bot 绑定与新闻分配

状态：用户确认的目标设计。现有后台原型只有一组 Telegram Token 与主人配置；多 Bot 管理、分类投递和下述界面流程尚未接入运行代码。设置预览只模拟状态，不接收真实 Token，也不发送消息。

## 机器人管理

在“推送与运行”顶部提供机器人列表，而不是只放一个全局 Token。用户可以添加多个 Bot，用自己的名称区分，例如“综合新闻”“数码关注”“成人专栏”；名字只是用途备注，不代表自动创建了真实 Telegram Bot。

每个机器人分别配置和显示：

- 本机配置 ID、显示名称、启用/暂停状态。
- Bot Token：正式 App 输入后保存到 macOS Keychain，界面掩码显示；普通配置仅保存 Keychain 引用。
- 验证 Token 后得到的真实机器人 ID、用户名、验证时间与连接状态；不能把用户填写的备注当作已经验证的身份。
- 主人私聊绑定状态、测试投递结果与最近错误。不同 Bot 独立验证、独立绑定，连接成功不等于已经可以推送。
- 已分配的分类与特别关注账号，避免删除一个 Bot 后才发现某些新闻失去目标。

添加流程：在 Telegram 的 BotFather 创建机器人或取得已有 Bot 的 Token → 在 NewsPaw 填写名称与 Token → 验证机器人身份 → 用户在 Telegram 打开这个 Bot 的私聊并输入本机生成的一次性配对码 → 确认主人绑定 → 发送用户触发的测试消息。配对码短时有效、一次性使用、不写日志；不能仅凭用户名或收到 `/start` 就认定对方是主人。

NewsPaw 仍为单用户程序。每个 Bot 都要验证私聊来自同一位已登记的主人；新增 Bot 不因此开放给其他 Telegram 用户。首次主人登记以本机生成的配对凭据完成。机器人 Token 不通过 Telegram 聊天或模型处理，只在本机设置里录入。已经被其他本机配置使用的同一真实 Bot ID 应提示合并或复用，避免启动两套更新消费进程。

## 哪些新闻发给哪个 Bot

分类与机器人是多对多关系，用户可以为一类新闻勾选一个或多个 Bot，也可以暂不指定而保持仅预览。以下仅为配置示例，不是已启用的订阅或实际绑定：

| 简报范围 | 示例目标 |
| --- | --- |
| 世界、日本、澳洲 | 综合新闻 |
| 数码电子 | 数码关注 |
| 普通 X 汇总 | 综合新闻 |
| `@elonmusk` 独立日更 | 数码关注，覆盖普通 X 的默认目标 |
| 日本 AV 产业、X 成人博主汇总 | 成人专栏，各自显式选择 |

特别关注账号默认继承所属内容分类的目标，也可以单独覆盖。普通关注账号进入所属分类汇总，其目标由分类设置决定，不为同一份合并简报暗中拆分收件人。界面应能直接看到账号继承自哪里、实际会发给哪些 Bot。

推送样式和接收目标是两个独立设置：给某个账号选择“AI 报纸”不会修改它的目标 Bot；改 Bot 也不改变文字/来源配图/报纸、新闻输出语言或计划时间。首版不提供隐含的“每个 Bot 不同语言”，所有最终新闻继续遵循全局新闻输出语言。

成人分类与成人特别账号不自动继承普通分类的目标；必须在相应成人分类或账号中明确选择。更改账号的普通/成人分区后重新检查其路由，旧分区的显式目标不自动跨分区保留。系统不会因为目标 Bot 不可用而把内容临时改发另一个 Bot。

无目标、目标暂停、未验证或未配对分别显示；不显示“正在推送”。如果一个分类选择了多个目标，其中部分不可用，已就绪目标仍可投递，不可用目标单独记录阻塞与原因，不能把整份任务标为全部送达。

## 任务与投递

简报按订阅与期次只生成一次，再为每个目标建立投递任务。同一份报纸发送到两个 Bot 时复用已经校验的图片，不重复采集、翻译或生图；样式、语言或编辑稿不同才产生独立版本。

每个回执至少按 `subscription_id / edition_id / bot_id / chat_id / part_id` 区分。内容去重不能跨 Bot 吞掉用户明确要求的第二份投递；同一 Bot 被多条路由匹配到同一期简报时只产生一份任务。独立分类、不同账号日更仍按各自订阅处理。

每个 Bot 使用自己的 Token、更新游标、配对状态和发送限流器。连接故障、Token 撤销、用户屏蔽机器人或媒体失败只影响相关目标，不暂停其他 Bot。总任务并发与模型预算仍由 NewsPaw 统一限制，增加 Bot 不自动增加采集或生图次数。

本机默认长轮询。每个 Bot 接入前检查已有 webhook 与重复消费者：已经被其他应用接入时显示冲突，不静默删除原 webhook 或丢弃未处理更新。切换接入方式作为明确的设置操作，不能把“验证 Token”做成会改变原服务的动作。轮询游标与去重记录按 Bot 隔离；某个 Bot 的限流只暂停它对应的发送队列，并遵守返回的重试时间。

修改分配影响新期次及尚未开始投递的任务，重新计算这些任务的目标；已送达消息不自动复制、撤回或重发。暂停、删除或解除绑定立即阻止该目标后续发送，并取消其尚未发送任务。已经部分投递的期次保留回执与部分完成状态，不把剩余消息块静默转移到新 Bot；需要补发时由用户明确重试整份或未完成部分。

删除 Bot 配置时展示受影响的分类和账号，保留历史投递回执，不删除新闻证据。重新启用或修复连接后只按对应订阅的补发窗口处理，不把长期积压消息一次全部发出。

## Bot 内交互

每个 Bot 只接受已绑定主人的私聊。可操作范围包含当前 Bot 被分配的分类，以及实际目标中包含该 Bot 的特别关注账号；单账号分配不扩大为整个所属分类的权限。例如“数码关注”可以查询已分配给它的马斯克日更，但不因此接收全部普通 X 汇总。成人内容也不能因为从另一个 Bot 发了模糊请求就改走普通处理组。App 是管理所有 Token 和全局路由的入口，聊天只提供明确作用范围的查询、预览、暂停和状态操作。

界面预览的“演示验证”“演示配对”和“演示测试”只展示流程；不采集真实 Token、真实配对码或 Chat ID。只保存虚构 Bot 配置 ID、备注、路由与演示阶段，不能用预览状态启动实际驻守或推送。

## 验收重点

1. 两个不同 Bot 可独立验证、绑定、暂停和测试，任意一步失败不污染另一个 Bot 的状态。
2. 世界新闻发 Bot A、数码新闻发 Bot B；同一分类显式选 A+B 时各送一份，模型只生成一次。
3. 特别账号可继承或覆盖分类目标；关注级别、样式、目标语言、发送时间互不改写。
4. 成人分类不会默认发到普通目标；分区切换后重新检查路由与待投递任务。
5. 未绑定目标不会发送；删除或解绑会停止后续投递，保留已经发生的回执。
6. 任意 Bot 故障不触发换 Bot 兜底、不跨分区调用模型、不重复生图；部分送达状态可查看。
7. 机器人管理与分类目标在简体中文、English、日本語界面中均可操作，新闻输出语言独立保留。

## 官方接口依据

- [Token 认证](https://core.telegram.org/bots/api#authorizing-your-bot) 与 [getMe](https://core.telegram.org/bots/api#getme)：用各自的凭据验证各自的机器人身份。
- [Bot 与用户的区别](https://core.telegram.org/bots#how-are-bots-different-from-users)：用户需要先向相应 Bot 发消息建立私聊，绑定一个 Bot 不会自动启动另一个。
- [getUpdates](https://core.telegram.org/bots/api#getupdates)、[webhook](https://core.telegram.org/bots/api#setwebhook) 与 [getWebhookInfo](https://core.telegram.org/bots/api#getwebhookinfo)：更新流与确认游标属于对应 Bot；同一 Bot 的 webhook 与长轮询不能同时使用。
- [发送限制](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this) 与 [retry_after](https://core.telegram.org/bots/api#responseparameters)：按实际返回执行限流退避。共享持久化队列与按 Bot 分区是 NewsPaw 的设计选择，不是 Telegram 额外要求的全局额度。
