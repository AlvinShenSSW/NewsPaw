# AFK 开发交接

参考仓库：https://github.com/AlvinShenSSW/afk 。当前已加载插件 1.3.7。项目配置为 Codex 主导、单一 Kimi 独立外门；它也是最终外部审阅，不能声称有两位独立 reviewer。

Kimi CLI 已由 2.1.1 升级至 2.5.2，`kimi provider list` 显示可用 `kimi-code/k3.1-pro`。评审调用显式固定这个 alias，并记录选择；CLI 最终文本不是服务端模型身份签名，不伪造 observed identity。正常新闻运行模型与开发 reviewer 是两套配置。

本机 `.afk/config.md` 保存 test/lint、插件路径、`gates: kimi`、`priority: kimi`、`policy: leave-open`。本轮只规划与设计审阅，不启动 AFK 全流程；未来先接收明确的 issue 编号及范围。epic 不适合作为一个巨大 PR，优先把子 issue 逐个执行；依赖完成后再进入其子任务。

## 推荐顺序

1. M1 基础：O03、F01、F03 → F02/F04 → S01、M01/M03 → M02/M04；T01 和 U01 可在依赖就绪后并行排队。
2. M1 文字闭环：Q01/Q02/Q03、T02/T03、S04、U02/U03；S02 补来源；O01/O02 形成可安装、可诊断的 Mac 产品。
3. M2 完整首版：S03/S05、X01/X02/X03/U04、D01/D02/D03。功能依赖以 backlog/GitHub 中的具体列表为准，顺序列表不是额外依赖。
4. Later：X04 重大提醒与视频，需另行交付范围；不影响普通定时新闻上线。

M1 不包含 X、AV 真实订阅和报纸生图；M2 完成后才称为本次完整首版。M1/M2 都需执行对应端到端验收与安装检查，不能把某个 epic 单独完成当成整个阶段完成。O03 初始提交提供 CI 框架，后续子 issue 必须添加自己的测试并更新阶段验收记录。

## 每个子 issue 的完成条件

范围与非目标冻结；依赖已完成；验收对应自动或具名人工验证；不改变既定 mockup；失败状态可见且无真实秘密；内部检查与 Kimi 外门有效；最终 revision 检查通过。真实凭据不可用只留下对应联调未验收，不能标全功能通过。

官方政策/模型/来源会变：接入时重新验证，不照抄旧文档接口假设。用户确认已领取 OpenAI Pro $100 档 API credit，NewsPaw 用其绑定组织项目 Key；本轮未读取账单。文本、OpenAI搜索/生图共用该组织余额，X/备用供应商另计。预算以程序预留与实际 usage 为准，套餐说明不是自动支出授权或精确余额。
