# X01 / #23 — account identity and List classification

## Frozen contract

Manage the single owner's explicitly supplied X handles and Lists. Track a verified stable numeric account ID across username changes, deduplicate identities, and distinguish unavailable, private/protected, permission, authorization, throttled and unverified states. List discovery preserves per-member classification and cannot feed unclassified or adult accounts to an ordinary route. A partition change clears incompatible subscription, targets, time/style overrides and returns durable invalidation information. Priority is separate. No automatic Elon Musk/adult account seed, post collection, model invocation or send. X02 owns timeline/cursor collection and X03 the editions.

## Design

- Add the missing X bearer credential slot to the existing config as x_api with only a Keychain reference. Bump config schema 3 and add an upgrade from existing schema 2 in the next SQLite migration; preserve old accounts, model/Bot state and legacy history. Extend CredentialManager's same protected save, fresh reference rotation, cleanup journal and status path with explicit kind x_api and ID x. Never store or echo the bearer, accept a custom X host, or import real credentials silently. Verification evidence tied to an old credential reference is historical and cannot authorize collection with a new key. Keep the effective routing contract version at its existing value 2 rather than copying the document schema into the fingerprint; this additive slot cannot invalidate normal or adult frozen preparation. Preserve untouched legacy-import eligibility when its recorded revision matched before upgrade. Never rewrite persisted Q01/M02 route snapshots.
- Keep account choices in current app_config accounts. XDirectory accepts normalized handle (optional @, 1–15 ASCII alphanumeric/underscore) and List numeric ID or canonical x.com/twitter.com List link. Repeated case-insensitive handle and repeated List ID are idempotent. New account draft has no remote ID or enabled route. Optional explicitly chosen partition remains separate from priority; unclassified entries have no subscription. Manage special/ordinary priority and compatible explicit X subscription through existing credential-manager CAS; priority switching clears incompatible standalone times/style/target override. Reuse T02 account_partition for changes and report affected account/subscription scopes and durable revision. No standalone authority from stored ordinary override. Route/content and settings already use F02 fingerprints; do not invent an event bus.
- SQLite x_identities binds stable remote account ID (unique), local account ID, canonical handle, observation state, credential reference, checked time and direct-follow flag. No reliance on an advanced config claim alone. A verified identity is rechecked by numeric ID, retaining local ID on rename; an initial lookup by handle must match any requested existing ID. On a duplicate remote ID, expose canonical local account and avoid a second verified subscription; a bare unrouted duplicate draft may be removed only if it has no separate choices. Never overwrite a different canonical route. Track identity unavailable/protected after an authoritative lookup so X02 cannot proceed using old ready state. Export one current account binding/readiness method for X02 that requires present authorized identity, matching credential and config remote ID/handle, explicit partition/route and direct-follow or active membership.
- SQLite x_lists stores stable remote List ID, safe name, explicit budget partition, optional owner-approved default-adult rule, state and latest complete member snapshot. Existing identities are reused by stable ID. Normal or mixed Lists add previously unseen members as unclassified drafts with no subscription/targets; a user-selected adult List may initially classify unseen members adult but leaves routing unassigned. Existing classifications and choices are never inferred or reassigned by membership. Membership removal only follows a complete validated pagination; absence from a truncated/error response is not removal. Keep known accounts and history. A list-only account without any current complete active membership is no longer eligible; explicit direct follow can independently keep its scope. An explicit user follow can mark an existing account direct. No model is used for classification.
- Reuse the safe transport with fixed https://api.x.com and app/user-provided OAuth bearer, GET whitelist for username/by-ID, List ID and List members, bounded responses, no redirects/retries. Request only id, username, protected and List name/private metadata. X List metadata privacy must be explicit; private List is reported without opening members. X permissions and inaccessible accounts are reported without asserting suspension unless the provider explicitly identifies it. Stable IDs are decimal strings, never floating point. Validate response type, matching requested ID, required protected/private booleans, page sizes, duplicate IDs/handles and bounded opaque next token. Do not retain raw bodies, bios or profile media. One explicitly triggered refresh reads metadata and at most four membership pages; default page size 25 and cap 200 usable members. Treat partial pages/errors/limits as incomplete, retain previous complete membership without advancing coverage. Future scheduled readers need only confirmed current directory results.
- Reuse M03 X-read meter for all explicit directory requests. A requested page reserves max_results, one identity/List metadata request reserves one; settle conservatively to at least one app read for a known response or the number of rows actually returned. These are local read units, not provider charges. Unclassified metadata uses the ordinary read bucket until the owner classifies it; List uses its explicit budget partition, and individual account lookups use stable local account ID. Unknown response keeps reservation and does not auto-retry. Use one x_operations row per request ID (kind, scope, frozen arguments, safe status/result and page receipts) to dedupe repeated button presses across restart. Repeated exact request returns durable state; different args conflict. Serialize active operations for the same scope, preserve uncertain results and show limits/errors. Create unique per-page budget intent atomically with active operation before each GET. Re-read configuration revision and exact credential/identity before effects and again at completion; stale results settle accounting but cannot update identity or membership. Startup classifies abandoned in-flight rows under existing process lock and does not read X.
- Apply config/identity/membership changes atomically. Extract the existing Store save_config write body as one internal caller-transaction helper shared by save_config, commit_credentials, import_legacy_config and X directory writes. Preserve provider/source/Bot hooks and add only an X identity revocation hook. In the same transaction mark old X identity evidence stale on account deletion or handle/remote ID change; exact delete/re-add and A→B→A cannot revive ready. An authoritative X rename saves the changed config (revokes the old observation) and current verified observation atomically in that transaction. When writing X identity from a List, apply the same order. Partition/priority changes retain identity but invalidate affected route via F02. In-flight requests also fail current config revision/ref checks, and a CAS rollback cannot leave evidence revoked. Preserve credential lifecycle write protection. X identity is valid only for currently present account/config/reference; delete/re-add or input mismatch cannot revive another account's evidence. Issue operations through existing same-UID ControlServer: list/add accounts, classify/assign/priority, verify/read status, add/refresh Lists and inspect complete/incomplete membership. All mutations require explicit input/CAS or idempotent operation identity. Bound outputs and expose only safe current metadata/reasons. No remote writes.
