# Q02 / #28 — independent Telegram outbox receipts

## Frozen contract

Send the same frozen edition to each explicitly assigned, currently authorized private Bot. Receipt identity is subscription/edition/Bot/chat/part. Multiple paths to one binding share its receipts. Keep known acknowledgements and unknown sends apart. Revalidate the exact pinned Bot binding, current assignment, adult permission, job control and edition before every effect. One unavailable target cannot hold up another. A paused, deleted or unbound Bot cannot continue. Preserve legacy history and the existing mockup.

Q02 consumes Q01 and T01/T02 in the existing single backend. Q03 owns automatic scheduling, catch-up deadlines and replacement of stale unsent generations. D01/D02 own choosing, producing and checking actual photos. T03 owns chat commands and test sends. Q01 currently exposes frozen text or explicit text fallback. Q02 implements the independently acknowledged photo transport without adding a generator or asset downloader. No startup send, fallback recipient, automatic ambiguous retry, provider exactly-once promise, message editing or legacy replay.

## Design

1. Add schema 13. One immutable delivery manifest per Q01 job, one target row per (job, Bot), pinned Binding, chat and Telegram Bot ID. Store a bounded typed part-state list and bounded attempt receipts in each target row, indexed by immutable manifest part index. Transactional read/modify/write protects each target. A nullable inflight_part plus a partial unique index by Telegram Bot ID limits each Bot to one send in flight across jobs. Store absolute per-target backoff_until and index by remote Bot ID. Maximum future backoff for that ID holds only that Bot, including other jobs and new credential generations. Rows survive deletion, cancellation and expiry. No new server or worker framework.
2. Build one immutable manifest from ready Pipeline input and EditorialService.render. A job ID denotes its exact frozen edition and subscription/account. Preserve all citation links, news locale and plain text. Reuse the existing UTF-16 splitter as a shared utility, preferring line boundaries and preserving complete HTTPS links; refuse an oversized citation line rather than split its URL. Cap parts and total encoded size. Disable link previews. When a later trusted media stage attaches one or two photo descriptors, pass opaque local asset ID, SHA-256, MIME, validated dimensions and localized caption. Read bytes through an injected trusted asset resolver, recheck size/hash, and use a fixed safe filename/multipart upload. No RPC pathname, remote URL upload or arbitrary binary in configuration/database. Adult photos are spoilered. Text and photos are separate ordered sends, one receipt per photo; no atomic album assumption. Text and citations remain present if a photo fails.
3. Read current effective route for the same subscription/account/style. Reuse Q01 profile generations. Compare content after excluding only the per-Bot projections and target-only blockers. Owner, account, enabled state, partition, locale, sources, profile generation, style and timing remain frozen. On stale content, stop all remaining sends for the edition and preserve historical acknowledgements/unknowns. Job pause stops future effects and permits already dispatched work to settle; job cancel stops future work. Use TargetManager.preview and revalidate_target for current selected IDs and live Binding authorization. One blocked Bot gets its own diagnostic. Exact bot/chat/generation never switches silently, even if another Bot or a new generation is available.
4. Enqueue idempotently creates shared manifest and per-selected target rows. Before the edition has any send intent, reconcile explicit assignment changes: add newly selected IDs, revoke removed IDs, and only reselect under the same binding with no lifecycle invalidation. A target whose binding changed is never repinned implicitly. A target initially unready is visible without authority until an explicit owner requeue or future eligible edition. After any intent, freeze recipient addition for this edition; assignment removal still revokes its Bot, and authorized peers continue. Final request-time transaction checks the same scope to close races against the first intent. Partial delivery never migrates unfinished parts. Reconciliation itself performs no send.
5. One explicit advance(job, Bot) attempts at most one part. Check prior part order, eligibility, current binding, and remote Bot backoff. Await pinned Keychain read and optional bounded local asset read. In Store._write repeat job/route/assignment/binding, part and backoff checks, then record the unique attempt ID, timestamp and inflight state atomically. No POST if intent fails to commit. Multiple workers may read credentials, only one can claim the part. After durable claim, pass only that pinned binding and frozen part to the typed client. Update state/receipt atomically by matching attempt ID. On real startup under the exclusive process lock, recover all unfinished sends to outcome_unknown; elapsed time cannot release an ambiguous part. Keep prior success. Unknown blocks later parts for that target; other Bots can continue. Explicit local duplicate-send acknowledgment may re-arm the same unknown part after current preflight and within finite retry policy, retaining prior attempt. Owner-observed success or skip has separate evidence classification and does not claim Telegram confirmation. Never rearm a permanently revoked binding automatically.
6. Keep GET whitelist in TelegramClient.call. Add typed send_message/send_photo against the same fixed TLS origin, redaction, bounded response, no redirects/retries. HTTP 200, ok=true, positive Message ID and exact expected private chat are required for confirmation, with sender matching if supplied. Malformed/mismatched success, transport error, cancellation after claim, oversized data and unexpected status/server error are unknown. Explicit valid Telegram ok=false with matching HTTP/code can give known 400 (payload rejection), 401 (token revoked), 403 (blocked) or 429. Honor valid retry_after or conservative delay when absent; invalid range holds instead of retrying too early. Limit automatic 429 retries per part. 401/403 revoke only the still-current pinned generation through existing T01 state/projection in the receipt transaction, without poisoning a newer Bot generation. Never accept chat migration. No raw error text, response, token or media in logs/status.
7. ControlServer owns one Outbox using the existing Pipeline and TargetManager. Startup recovery runs under its lock. Same-UID read-only receipts/status and explicit local unknown resolution are exposed. No arbitrary send/enqueue RPC. In-process enqueue/advance are the normal scheduler entry points for Q03. Preserve legacy NewsBot except sharing the splitter. Status reports per-target pending/partial/delivered/unknown/revoked/blocked, bounded receipts and backoff with safe reasons.
