# T03 / #32 — authorized Telegram commands in the resident backend

## Frozen acceptance

Implement #32, R04 and R08 on the exact reviewed Q03 prerequisite. One backend, one owner, multiple private Telegram Bots. Treat each (subscription, special account or no account) as a separate scope. A special account never grants the aggregate subscription or siblings; adult requires explicit Bot permission. The incoming owner identity and pairing generation come only from the typed, durable BotRegistry inbox. Every scope is checked before reading a brief, changing a setting or staging a reply, and again before any send intent after asynchronous credential access. A cross-Bot/rebound/revoked brief reply reveals no content. UI locale renders controls, output locale renders validated news. Keep the optional legacy single-Bot developer CLI outside production; add no parallel polling connection or model command execution. Update the prototype warning only if needed to distinguish which entry point these commands use.

## Deterministic commands

- Use literal /news, /search, /schedule, /pause, /resume, /status, /why and explicit /x, /av, /paper entry points. Match optional @username only for the verified receiving Bot. Select with stable s:<subscription-id> or a:<special-account-id> displayed alongside names in a bounded list of currently authorized scopes. Prefer an explicit selector or a valid Telegram reply; when both appear require exact agreement. Invalid explicit or reply anchors never fall through. A Bot with one eligible scope can default for an unanchored message. For a mixed or multi-scope Bot request an explicit selection, including with media. /x restricts to X categories and /av to AV; neither upgrades access or implicitly combines multiple matching scopes. Status/help/prompt contain no raw chat echoes or credential detail. No user-controlled text or media goes to a model in T03. Free text with an exact resolved scope uses bounded local search. Media can carry a scope selector in its caption or be a reply to an authorized scoped message; for unsupported capability reply with instructions to send text. D03 reuses this typed resolution before any future media download; D02 reuses /paper only after generation exists.
- Derive scopes by enumerating current enabled subscriptions and current special account rows from the config, then use TargetManager.revalidate_target and exact Binding (Bot ID, remote ID, chat/owner and generation) for eligibility. Use bounded display paging if necessary; a valid known selector remains directly usable even when its scope is outside the first display page. Use no broad target status/error dump. For a reply anchor, require one exact confirmed message_id belonging to the same Bot, private chat and live binding generation, in the Q02 target receipt or this command's confirmed scoped reply. Match typed stored binding, not just chat/message number. No owner-confirmed or uncertain substitute. Resolve to the frozen job/scope, never to an untrusted brief ID. Check the live scope after lookup. Scope-only command responses can serve as context for the next media message but /why needs a matching edition. Exclude general guidance replies from scoped resolution.
- /news returns the latest eligible frozen result for exactly the authorized scope, or the requested receipt-linked result. Use Pipeline.delivery_scope or an equivalent shared content check so stale partition, account identity/member/source and output-language changes cannot release old editions. Render validated existing briefs in the configured output locale, preserving citation lines. /search searches only bounded recent validated results in that same live scope, casefold matching on localized titles/body, with bounded query length and results. Include complete original links and date, never label it live. /why shows selected edition's validated citations and coverage (no raw hidden evidence or prompts). Avoid global jobs/status queries followed by arbitrary filtering. Use indexed scope/time lookups with per-scope caps.
- /schedule <scope> shows only that scope's times and IANA time zone. Accept explicit comma-separated HH:MM to replace the selected scope's times under current configuration CAS; do not change global policy, timezone, partition, owner, locale or other scopes. An actual aggregate time change is rejected inside the same transaction if any linked special account inherits that subscription's times, even if the current Bot also holds a separate assignment for that account. A no-op remains valid. Show an instruction to change it in Mac settings and never create an override on another scope. A special account's inherited schedule can be read without mutating the subscription; setting times writes its own override. /status shows only current selected scope jobs/occurrence status and safe localized explanations. /pause and /resume use the exact current authorized job (or explicit valid receipt anchor where it is resumable). Do not toggle Bot/whole scheduler, bypass schedule consent or retry blocked/unknown paid work through chat. Use the pipeline's absolute pause bit and event, applying its existing local cancellation nudge after commit when appropriate. No resolve-unknown command. /paper reports the current capability boundary without dispatch until D02.
- Small three-language template map for help/status/errors/times and scope prompts. News, including search excerpts, comes only from currently authorized editions already validated in the active output locale. Dated evidence links remain source-language links; publisher names and handles remain as supplied. Revalidate current UI locale or stop remaining management parts if it changes; likewise never mix output locale across parts.

## Durable dispatch

Add one bounded command consumer in ControlServer with isolated start/close and per-iteration work cap. Reuse typed Bot inbox keys, binding and existing TelegramClient.send_message / split_delivery_text. One small companion receipt table keyed (bot_id,generation,update_id) stores frozen validated response parts, scope/job anchor as needed, current binding identifiers without raw token, safe result states/message IDs, per-part intent and bounded 429 backoff. In one Store._write transaction verify current inbox/binding/scope, calculate the response, apply idempotent scope-setting/absolute pause mutation through existing Store/Pipeline transaction logic where needed, stage the reply and move inbox state out of pending. No transaction remains open across awaits. A change from another UI write wins or causes CAS/reauthorization failure before any mutation. After resolution erase terminal input body from command-owned history while keeping inbox ID tombstone and authorized reply anchor. Do not retain raw token, arbitrary media bytes, user query or provider input in receipt. Do not run a mutation again after reply failure or process restart.

Revalidate exact live authorization and frozen context immediately before each staged part intent after credential read. No part sent if current check fails, no fallback Bot. Commit intent first, then typed sendMessage with previews disabled. Persist confirmed Telegram message ID; confirmed 429 uses a bounded retry and shares its remote Bot backoff with Q02; terminal known failures and unknown outcomes stay distinct, stop remaining parts, and never automatically replay unknown. Use a single shared Bot lane check inside each command and Q02 immediate transaction, comparing both durable receipt tables by verified remote Telegram identity for in-flight intents/backoff. Reuse revocation logic for 401/403, preserve other Bots. Clear interrupted intent to outcome_unknown only on startup under the control process lock; cancellation/loss of response after intent follows same rule. For newly finalized or revoked rows keep only minimum tombstone and message evidence, preserving Q02 historical receipts.
