# F02 / #11 — Effective routes for one owner and multiple Bots

## Spec and frozen contract
One Mac/server, one backend/database/owner, multiple owner-paired Telegram Bots. Resolve source → subscription → explicit normal/adult partition → same-partition primary/backup → global news language → style → selected Bots. Preview is pure local data: no model, credential read or network. A route is explanatory, versioned and revalidated before later side effects. This issue defines that execution contract; queue executors, model capabilities/credential checks and Bot verification workflows remain downstream.

Acceptance: inheritance/overrides never mutate upstream configuration; incompatible references rejected on save; unclassified sources/accounts cannot select any model. Adult targets must be explicitly selected on subscription/account and adult-enabled. Persisted config revision is the durable invalidation signal; route fingerprint distinguishes execution-relevant changes from UI-only locale changes. Removed/disabled sources, accounts, profiles, targets, owner/binding, changed language/schedule/style invalidate old route; previews never execute.

## Approach and decisions
Extend document/database to version2 with a small transactional migration (existing backup/rollback machinery). Add group_styles normal/adult=text; category style nullable; account style nullable; subscription style nullable (existing text values retained). Precedence explicit request style > special-account style > subscription style > category style > group style. News output locale always global; UI locale does not affect route fingerprint. Account overrides only for priority=special; bot_ids=None inherits subscription, [] explicitly means no target; times=None inherits, [] means no scheduled slot. Sources have no hidden targets/schedules. Explicit source_ids select that set; [] selects enabled sources assigned to this category. Explicit source must actually belong to subscription category, never silently infer from partition alone. Disabled selected sources block execution; unselected disabled sources ignored.

Source/account partition=None is an unclassified draft. Such sources require empty category_ids and disabled state; such accounts cannot bind a subscription. Config can save them, but route resolution returns blocked without choosing profiles. Classified account subscription must have matching partition; no guessing by model or supplier. Profiles enforce role and partition for explicit category overrides and fixed default IDs normal_primary/backup, adult_primary/backup when used. Missing default profile blocks route, rather than substituting another group. Adult bot selection is explicit and requires adult_allowed even before activation; normal targets do not require it. No global default Bot and no per-Bot backend. Normal/adult may use same Bot only with explicit adult opt-in and same owner pairing.

Pure resolve_route(config, revision, subscription_id, account_id=None, style=None) returns an immutable snapshot with canonical serialized effective payload, fingerprint, blockers and explanation. Payload includes subscription/category identity, effective input sources (id/kind/url/partition), account identity/remote ID/handle/priority, profile configuration incl credential references/capabilities, news locale, timezone/times/style/max_items, owner and effective Bot identity/refs/binding/adult permission. No secret values. Consumers get fresh decoded copies; mutating a preview cannot rewrite its fingerprint or config. Account IDs must bind the requested subscription; unknown/unclassified records produce explicit blockers and no profile. Invalid config raises ValueError rather than partially routing it.

Static blockers include disabled subscription, no selected enabled non-draft source for non-X routes, missing account stable remote ID for an account route, missing model slot/credential reference, no target, missing owner and no ready target. Per docs/telegram-routing.md, an unverified/unpaired target has its own diagnostic and never blocks a different ready target. Snapshot targets retain all selected identities/binding states for invalidation; bots contains only the executable subset. Re-pairing a target changes the snapshot. Credential refs do not prove that Keychain items exist, nor do capabilities prove live availability; downstream must validate those immediately before use. Aggregate x/x_adult subscriptions can represent a route without RSS sources, but snapshot their effective member set (classified matching subscription, ordinary priority; special accounts default excluded), including stable ID/remote ID/handle/partition/priority. Missing members or missing stable remote IDs block aggregate execution. Member deletion, movement, partition or priority changes alter the fingerprint. X module later performs network collection; it must use these snapshotted members. Preview reports this boundary explicitly, not an available live timeline.

Store.config_revision() reads durable revision cheaply. Every successful save already increments it in the same transaction; no event bus/table is necessary. Store.preview_route wraps current config+revision. Store.revalidate_route(snapshot) freshly resolves from current DB using snapshot selection; reject blocked or changed fingerprint as RouteBlocked/RouteStale, return fresh snapshot if execution semantics unchanged even if revision changed. This is a preflight, not a lock across network I/O; Q01/Q03/T02 consumers must call immediately before each side effect. It does not authorize or perform sending.

## Migration and compatibility
Version0 initializes latest schema/config directly; historical version1 upgrades its document via explicit v1→v2 transform (add only new fields, preserve all prior values). Migration increments revision to invalidate existing snapshots, validates transformed config before commit, keeps cutover/history untouched. New initializer remains revision1 so explicit legacy import still works. Preserve pending explicit import eligibility through migration_info: on v1 upgrade only when old revision=1 and no legacy_imported marker, record untouched_import_revision equal to the new revision. Importer compares current revision to this stored eligible revision (default1). User saves then advance beyond that revision, so edited configs remain protected. Existing database v1 that contains relationships newly rejected (e.g. cross-partition account/unsafe adult target) must fail upgrade with original DB and backup intact; do not silently reclassify or start tasks. Tests record that repair requires an explicit configuration correction using matching older version, no auto data loss. Version2 migration is idempotent and old F01 binaries reject newer database via existing version guard. F01 minor owner0 compatibility remains F04, unrelated here.

## Allowed surface / non-goals
Write app_config.py (schema/defaults/validation/upgrader), migrations.py (version dispatch), new routing.py (pure resolver/snapshot/errors), store.py (revision/preview/preflight), focused tests and this spec. Read existing config/store/news consumers and requirements/mockup. Execute uv run pytest -q, uv run ruff check ., uv build; outputs .pytest_cache/.ruff_cache/dist ignored. No secret access, live calls, mockup changes, queue execution, routing cutover in old service, model fallback/budgets, caching engine or distributed system. Older runtime consumes legacy config until later composition issues wire the new route contract.

## Risk and tests
Highest risk is silent cross-partition reuse or stale target dispatch; table-driven tests cover all priority levels, same-group model overrides, both cross-group directions, unclassified sources/accounts, deleted references, mixed ready/unpaired targets with healthy continuation and unavailable-target exclusion, explicit adult targets, account inherited/empty targets, changed Bot pairing/owner/credential/source URL/model/language/partition/schedule/style and disabled subscriptions. UI locale/name changes must not stale a route. Test snapshots cannot mutate parent or stored effective value; preview works under offline guard with no model/keychain. Store CAS revision notification/restart and revalidation; aggregate member removal/move/partition/priority invalidation; untouched-v1 upgrade permits explicit legacy import while edited-v1 upgrade still refuses; v1 upgrade preserves values/backups/history, failed upgrade rolls back, repeated open stable. No external system behavior assumed here beyond existing tested SQLite transaction machinery.
