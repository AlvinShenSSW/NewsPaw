# T01 #30 — personal multi-Bot identity and pairing lifecycle

## Spec review / frozen contract
One owner, one backend and database, several Telegram Bots with separate credentials, identities, pairing, update cursors and connection status. Implement local registry/control actions and bounded polling. Validate token with read-only getMe/getWebhookInfo; do not steal webhook or silently compete with another local Bot registration. Pairing requires a short-lived one-time high-entropy code, private chat and numeric identity. /start, username and claimed config flags grant no authority. Pause/unbind/delete/token rotation revoke the binding version immediately. No groups, other recipients, paid model calls, news sends, command handling/media downloads (T02/T03), native UI (U03), or new service/process per Bot. Existing mockup unchanged.

## Acceptance / authority decisions
- `BotRegistry.status/list` combines config references with authoritative SQLite registration. Unregistered config Bot is unverified regardless of legacy config `verified/paired/chat_id` flags. Registration is created only by local explicit verify; no credentials read on status. Verified Telegram ID must be positive integer <=2**52, is_bot exactly true; store bounded username/name as display only. Current credential reference and registry generation checked before and after every awaited key/network operation.
- `verify(bot_id)` reads current Keychain token, calls getMe and getWebhookInfo only, rejects malformed result, revoked token, active webhook, or duplicate active Telegram ID. It does not call getUpdates/sendMessage/deleteWebhook/setWebhook. Store webhook_present boolean rather than raw possibly secret URL. Duplicate ID check occurs in the result transaction, including concurrent verifications. Paused/unpaired registrations still reserve their ID; deleted records do not. A same-generation failed verification revokes runnable status; stale results cannot overwrite a rotated/deleted registration. HTTP409 visible consumer_conflict; cannot enumerate other external long-pollers. UI status includes token_exclusive_required; no claim of exclusive remote ownership.
- `pair_code(bot_id)` local only, verified/conflict-free registration, generates secrets.token_urlsafe(24), expires10min, max5 wrong attempts; store salted hash and expiry/attempt count, return plaintext once in RPC response, never logs/audit/inbox. New code invalidates old code; code hashed with compare_digest; successful comparison and binding/cursor consumption atomic. No replies sent by T01. Local UI can show success by status; T03 later adds authorized replies.
- Incoming `/pair <code>` only from a normal private message whose sender is a non-Bot and numeric chat.id == from.id >0, timestamp not before code issue. Reject channel/business/edited/group payloads, usernames, /start and malformed code. If global owner unset, first valid code atomically establishes owner; otherwise exact numeric owner match required. The same owner must pair each Bot independently. A valid code from wrong owner cannot reassign ownership; counts against limited attempts. Pair code consumed once even if HTTP poll result repeats or process restarts.
- `pause/resume/unbind/delete` local mutations increment persistent binding generation; pause stops polling/dispatch, resume preserves verified bound chat but does not replay old commands, unbind clears chat/code and polling, delete removes config via existing credential lifecycle and retains registry tombstone/history. Token reference rotation/deletion, owner ID change and removal/re-addition invalidate registry generation + verification/binding/code in the same Store configuration transaction. Direct config changes to existing bot identity/verified/paired/chat projections cannot create authority; registry is authoritative and recomputes projection. No new schema fields in app_config required.
- Authoritative `snapshot(bot_id)` / `revalidate(snapshot)` includes registration generation, credential reference, remote Bot ID, owner/private chat, pause/verified/pair state and presence. It rejects unregistered/paused/unpaired/conflicting/revoked/stale bots. T02 outbox must call it before every external effect; existing F02 route config remains routing evidence, never sufficient send authorization. Unit pure-config route behavior remains compatible; no attempt to retrofit legacy prototype transport here. U03 status must use registry, not legacy projection. Current control-mode runtime remains the intended configured system; legacy `.env` prototype explicitly not activated by this work.

## Polling and lifecycle
Use fixed official HTTPS api.telegram.org origin with token path generated from strictly validated token (digits:ASCII URL-safe secret), no arbitrary URL/method, redirects forbidden, bounded2MiB response/35s deadline, no SDK retries or exception URL logging. Three allowed methods in T01: getMe/getWebhookInfo/getUpdates. Public transport F03 verifies DNS/connection; local httpx fixture injection only. Never persist token or raw API error description. Errors fixed codes revoked/forbidden/rate_limited/consumer_conflict/transport/malformed plus bounded retry_after seconds. Rate/cooldown applies per Bot, no global suspension.

`poll_once(bot_id)` one in-flight poll per Bot, timeout25seconds, limit100, offset last durable update_id+1 (no negative offsets/drop_pending_updates). Capture current generation before network; on stale result discard without advancing cursor. Allowed updates message only but validate every returned update (Telegram may return pre-existing other types). Batch update IDs integer>=0, monotonic sorted/dedup handling; malformed batch never advances cursor. Telegram IDs can restart randomly after long inactivity; confirmed offset usage follows documented API, no local assumption that IDs are timestamps. Cursor belongs to remote Bot identity: token rotation preserving confirmed same remote ID can retain cursor, different remote ID resets only after successful verify. Never transfer cursor to another Bot.

Process pairing and durable cursor in one transaction. Paired owner's non-pair private messages are kept in small bounded pending inbox for T03: only update/message IDs, sender/chat IDs, timestamp, text/caption and Telegram file identifiers/type/dimensions/duration (allowlisted fields), <=32KiB each. No raw full update JSON, no unowned messages, no pair codes, no file bytes, no model classification. New binding and resume establish inbound cutover timestamp; messages before cutover acknowledged as stale without command execution. Unsupported/unowned updates may advance cursor with fixed ignored reason. No deletion of Telegram messages or responses in this issue. Incoming code messages never stored as ordinary text even after code expiry.

Inbox max1000 pending per Bot; check available capacity before poll, and transactionally before committing batch. If capacity insufficient retain old cursor/entire batch unacknowledged, status inbox_full; resume after T03 consumption. SQLite faults roll back pair result/inbox/cursor together. Crash after local commit but before next poll returns same updates; update identity dedupe ensures no second action. No await inside SQLite transaction. Poll failures do not move cursor. Cancellation closes request, leaves known cursor, no send uncertainty because T01 only reads/acknowledges updates.

ControlServer owns one lightweight async polling task per explicitly activated registration (pair-code issuance activates; successful pairing continues). Shared Store/Keychain/client factory, one application process, no distributed leases/framework. Existing local single-instance flock prevents duplicate process; per-Bot lock prevents two service calls polling same Bot. On restart resume previously activated verified registrations; pause/unbind/delete cancel/disable future polls, postflight generation guard handles already-in-flight responses. Loop respects per-Bot next_poll_at/backoff and ends cleanly on ControlServer.close. Verification alone never starts polling. No automatic network for new/unregistered configs. Explicit control operations bots.list/status/verify/pair_code/pause/resume/unbind/delete are structured same-UID RPC, codes/tokens never in logs. Registry.delete calls existing CredentialManager config removal/cleanup path; maintain reference safety and affected route removal in one config mutation.

## Storage / approach
Schema10 (assuming S03 schema9 reviewed stack): bot_registrations row per local Bot ID retains generation, credential reference, numeric remote identity, verified/pair/pause/poll flags, owner chat, cursor, identity-cursor association, connection status/retry timestamp/cutover, pairing hash/salt/time/tries. Partial unique index on active nonnull remote identity. Inbox keyed local Bot ID/generation/update ID with sanitized payload/state; no message storage outside owner scope. Tombstones retain generations across delete/re-add. Existing Store save_config/commit_credentials/import write hooks invalidate known registrations atomically on ref/owner/removal; all consumers enumerated in tests. New config entries remain unregistered (status unverified), no implicit network or migration of prototype credentials/bindings. Migration clears legacy Bot claimed verified/paired/chat/remote fields only when first registry schema created; no trusting old demo state. Registry updates project compatible derived fields to config with revision bump for route invalidation. Actual lifetime authority still registry snapshot, so A-B-A cannot revive old delivery even if config fingerprint returns to previous value.

Use existing keychain manager; do not add a credential store. New modules `newspaw/telegram/{__init__,registry,client}.py` do not shadow external top-level python-telegram-bot. Legacy bot.py remains prototype until integration replaces entry path, documented as such; no running it through new pairing without matching authority. No real Telegram API calls in tests.
