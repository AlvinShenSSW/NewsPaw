# NewsPaw 架构 / 代码 / 产品功能 / 交互 审计与重构建议

2026-11-09 · 基于 `main`（aa4eeea，v0.5.0）与 `fix/macos-first-launch-backend`（209f121）· 只读审计，未改动仓库
设计稿：https://claude.ai/artifact/PqJ1KV8JtV1C7LXNyGW4Pt

前提（用户给定）：单人私用、一台 Mac、一个后台、推送到自己的 Telegram Bot；要简单好用、符合人的使用逻辑、不过度工程。

---

## 0. 一句话结论

后端在「不多花钱、不跨分区、不丢消息」三件事上是严谨的，值得保留；难用的根源不在这三件事，而在：

1. **同一个用户意图被拆成五个对象**：category / subscription / schedule scope / route / target，用户想的只是「世界新闻这一档」。
2. **四份各自带开关和 hold 的策略文档**（config、budget、schedule、newspaper/media），任何一个没填都**静默阻塞**，界面不告诉你卡在哪。
3. **界面是 RPC 的直译**：15 个模态 sheet、零内联编辑、零引导、所有错误共用一句「语言未保存到后台」、金额手填微美元、时区手填 IANA 字符串；首屏（订阅页）在后台未连接时是死胡同，不指向唯一能启动后台的「推送与运行」页。
4. **spec 19 / 21 / 29 把「不假设」写成了「不默认」**：Key 保存后不探测、价格未知就不派发、hold 不填就不准备。对单人用户这些应是内置默认值，不是阻塞点。

首次安装到收到第一份简报：**跨 4 页、约 9 个弹窗、约 35 次点击、11–12 个决策**，其中 4 个（源分区、调度总开关、model hold、能力探测）普通人完全无法预期。

## 1. 产品功能点审计

### 1.1 配置面规模（结构性原因）

- `app_config.py` schema v3：顶层 7 键 + 6 类实体 ≈ **60 个字段**；另有 budget 10 键、scheduler 5 键、newspaper 8 键、media 若干，**不在 config 文档内，也不在导出里**（`operations.py:264-269`，恢复安装会静默丢失）。
- 控制面 **≈75 个 RPC 操作**（`control.py:49-163`），mockup 五页只有 39 个输入控件。后端配置面是界面可见面的 2–3 倍，大量决策没有 UI 落点。

### 1.2 分类

**A 必需（保留并放到主路径）**
Bot token + 配对；一个可用模型 Key；分类勾选；每类时间；目标 Bot；新闻输出语言；普通/成人分区标签。

**B 有用但应有默认并隐藏**
备用模型（折叠为「可选：添加备用」）；按分类覆盖模型；每订阅多时间/独立时区（默认一个时间 + 系统时区）；catch-up 360 分钟 / lead 15 分钟（写死即可）；帖子类型（默认 original+quoted 合理）；max_items=5；来源配图 / 报纸 / 语音（已默认关，但报纸还要 3 个 profile + 3 个 hold，应合并为「开启报纸 → 选一个生图模型」）；OPML / GitHub / HF 连接器（按钮级）。

**C 过度工程（单人可手工管理）→ 简化方案**

| 现状 | 问题 | 单人替代 |
|---|---|---|
| 微美元三层预算 + 用户手填价格表 + cycle_day + 供应商额 + task cap（spec 21） | 用户只关心「每月最多花多少、已花多少」 | 一个「每月上限 $N」（可空）+ 实际用量；未知价格记为「未计价」，**不阻塞** |
| `schedule.holds` 不填不允许付费准备（spec 29） | 把预算内部约束变成用户阻塞点 | 内置保守 hold 常量，UI 不暴露 |
| `scheduler.enabled` 与 `subscription.enabled` 双开关 | 开了订阅不发，用户不知为何 | 订阅启用即进计划；「暂停全部推送」一个开关 |
| slot 稳定 ID / 墓碑 / 重排配对 / cutover（spec 29） | 为防改时间后重发引入的身份体系 | completed key 用 (subscription, local_date, HH:MM)。**未采纳**：会让同一天改时间后重发已完成期次，见 contract §6 |
| 5 种能力逐项探测 + untested / probe_unavailable 状态（spec 19） | 用户只想知道「这个 Key 能用吗」 | 保存 Key 时自动做一次文字探测；视觉/生图/语音在开启对应功能时才探测；TTS 永远 `probe_unavailable`，应隐藏 |
| ≥6 套独立 revision + 各自冲突码（`BackendModel.swift:55-57` 硬编码列表） | 为并发写者设计；单人只有一个写入端 | 保留 CAS，但 UI 不向用户展示「版本冲突」，自动重读重试 |
| 每 Bot 独立轮询游标 / 限流器 / webhook 冲突检测 | 2–3 个 Bot 不需要 | 保留 webhook 冲突提示，其余隐藏 |
| OpenAI 定向搜索独立配置、单次工具调用、单价预检 | — | 一个「允许模型补证搜索」开关 |
| 部分投递后目标变更要人工选 stop/continue（`delivery.resolve`） | 单人重复收到一条无伤 | 默认继续未变更目标 |
| 脱敏诊断导出 / 支持快照 / 导入预览三件套（spec 40） | 为「发给别人看」设计 | 「打开数据目录」+「导出设置」+「高级」里保留诊断 |

**D 概念重复（人会当成一个东西）**

1. category / subscription / schedule scope / route → **一个「简报」对象**；只在用户点「拆成国内/娱乐两份」时派生第二个。
2. source.focus + subscription.focus_weights + source_mode → 简报里**一个国内/娱乐滑块**，源只需勾选。
3. hold / reserve / cap / limit / budget / task_limit / quote → **「预算上限」和「已花多少」**。
4. group_styles / category.style / subscription.style / account.style / 本次选择 五层样式 → 简报级一个选项 + Telegram 回复时按次选「做报纸」。
5. subscription.bot_ids / category target / account target 继承覆盖 → 简报级**一个多选**；只有一个可用 Bot 时自动选中。
6. X：partition × priority × include_in_aggregate × subscription_id 四字段 → **「单独发 / 并入汇总」一个选项**，分区随标签页。
7. 六种「停」（退出 UI / 停止后台 / 调度关闭 / 订阅暂停 / jobs.pause / pause_category）→ **「暂停推送」+「退出」**。

### 1.3 心智模型映射

「每天早上 8 点把世界新闻发到我的 bot」：

| 句子成分 | 当前要碰的概念 | 问题 |
|---|---|---|
| 世界新闻 | category + subscription + ≥1 source（分区 + category_ids） | 源默认为空，用户不知道要先加源、给源选分区 |
| 每天 8 点 | times + timezone + scheduler.enabled + lead/catchup + slot | 默认 08:00 没错，但调度总开关默认关、时区默认东京而非系统 |
| 发到我的 bot | bots（token/verify/pair/adult_allowed）+ bot_ids + targets.set_subscription | 配对合理；「分配」在另一页另一步 |
| （隐含）用我的 Key | credential_ref + capabilities probe + schedule.holds + 价格表 | 三处不可见前置条件，不满足则静默 blocked |

### 1.4 默认值审计

| 决策 | 现状 | 建议 |
|---|---|---|
| 时区 | `Asia/Tokyo` 写死 | 系统时区 |
| 时间 | 08:00 … 22:00 内置 | 保留 |
| 普通 / 成人模型 | 4 槽已内置 | 保留 |
| Bot | 首个 Bot 不自动成为普通简报目标 | 只有一个可用 Bot 时自动选中；成人仍显式 |
| 预算 | 全 null 但 hold 不填阻塞 | 内置 hold；上限可空 |
| 价格表 | 空；未知即 `pricing_unknown` 阻塞 | 照常执行并标「未计价」 |
| 订阅启用 | 全 False | 可接受，但启用应一键且自动带出来源推荐 |
| 调度启用 | False，升级保持关闭 | 升级场景可理解；**首装跟随首个订阅** |
| 来源 | 空；25 条推荐目录不预选 | 开启某分类时默认带入该分类推荐源（草稿 → 自动试采集 → 启用） |
| 能力 | 保存不探测 | 保存 Key 时自动文字探测（花约 $0.001，问一句即可） |

### 1.5 保留清单（复杂但对单人也成立）

普通/成人分区隔离、禁止跨组回退与缓存复用（误送成人原文给 OpenAI 可能封号）；`outcome_unknown` 保留预留、不自动重试/切备（真实双重付费风险）；冻结简报 + outbox 按 subscription/edition/bot/chat/part 回执（Telegram 超时窗口真实存在）；一次性配对码、仅主人私聊；严格时间过滤与证据保留；Keychain + 配置只存引用；源文本视为不可信；迁移前备份；Telegram 命令按 Bot 作用域。
→ 这些都应**保留在后端、对用户不可见**，UI 只需在出事时给一句话和一个按钮（「结果未知 → 检查并补发」）。

## 2. 交互审计（SwiftUI 实现）

### 2.1 信息架构

五页沙盒式分区，每页一个 `ScrollView` + 一行副标题（Copy.swift:83-87，描述「查看…」而不是「做什么」）。**所有编辑都在 15 个 `.sheet`** 里，无内联编辑。首页默认订阅页（`BackendModel.swift:193`），未连接时只显示「启动后台后刷新」状态卡（`NewsPawApp.swift:185`），**没有链接到唯一能注册后台的「推送与运行」页**。

### 2.2 首次投递路径（实测步骤）

推送与运行 → 注册登录项 → 模型页 → sheet（provider / URL / 模型 ID 手填）→ 粘贴 Key → 存钥匙串 → 手填微美元 → 验证 → 推送与运行 → 添加 Bot → 填名字保存（**token 字段在名字保存前禁用**，无提示）→ 粘贴 token → 存钥匙串 → 验证 → 生成配对码 → 去 Telegram → 回来**手动刷新**（无轮询）→ 发测试 → 查结果 → 订阅页 → 添加来源 → 识别 → 勾分类 → 保存为未启用 → 预览采集 → 启用 → 分类开关 → 手填 `HH:MM` 和 IANA 时区 → 勾 Bot → 预览路由 → 保存并启用 → 推送与运行 → 定时推送 → 开启 → **手填普通/成人 hold（微美元）** → 保存。

### 2.3 反馈与状态

- 全 App 只有 1 个 `ProgressView`（XWorkspace.swift:208），其余加载 = 控件变灰。
- 成功几乎无反馈，保存即 `dismiss()`。
- **所有失败折叠为两句**：`.conflict` 或 `.saveFailed`（字面「语言未保存到后台」，Copy.swift:107），模型探测失败、token 被拒、OPML 坏、数字非法、加载失败全是这句。无 `.alert`。
- 原始值直接显示：source kind `rss/web/github`、ISO 时间戳、provider id、导入预览原始 JSON。
- 无确认的破坏性操作：解除配对、暂停 Bot、覆盖 token/Key、停止后台、停止并注销登录项、删除提醒规则。无撤销。
- sheet 在打开时捕获 `revision`，后台 3 秒轮询一旦 bump，保存就失败「设置已变化」——**用户什么都没改也会撞冲突**；`XAccountEditor` 甚至直接禁用保存（XWorkspace.swift:495, 572）。配对码停在 sheet 里直到手动刷新。

### 2.4 术语

四套互相重叠的字符串表（`Phrase` / `ConnectionCopy` / `SubscriptionCopy` / `XCopy` 等）。分区叫 普通内容 / 普通 / 普通新闻 / 普通分区，英文 General / Ordinary；后台叫 登录项 / 驻守进程 / 后台 / Backend / Resident / service；金额字段叫 微美元 而报表显示 `$0.12`；预留 / Held / Hold / 预算上限 / attempt cap 是同一概念的五个名字；「验证」指四种不同的付费/免费动作；「Run policy」标题复用于 Bot 暂停/测试/删除 和 X 提醒/视频菜单。

### 2.5 表单

需要手填且无选择器、无默认、无内联校验的技术输入：IANA 时区、`HH:MM, HH:MM`、模型 ID、API URL、8 处微美元字段、快照文件名、安静时段。非法数字的反馈是「语言未保存到后台」。

## 3. 架构与代码审计

### 3.1 Swift

- 最大视图：`XWorkspace.swift` 856 行（6 个 struct、4 个 sheet）、`NewsPawApp.swift` 425（shell + 订阅网格 + 推送页组合 + 语言页混在 `SettingsWindow`）、`XFeatureSheet` 267 行 28 个 `@State`。
- `AppModel` 只持 connection / config / bots / revision / busy / error；其余领域状态散在各 sheet 的 `@State`，通过字符串化的 `model.request(op, fields:)` 直连，超时按 op 名硬编码（BackendModel.swift:302-303）。
- `perform`/`run` 包装复制 5 次；「load → 改 dict → 带 revision 保存」模式重复 7 处；Cancel/Spacer/Save 页脚重复 11 处。
- 23 个测试全部是纯函数；视图不可测，无 UI / 快照测试。`swift build` / `swift test` 通过。

重构缝：typed `BackendClient`（每 op 一对 request/response struct）；共享 `EditorState`（revision + busy + failure）；`AppModel` 拆成 connection / config store / 各领域 store；一张带命名空间的本地化表；页面视图从 `SettingsWindow` 搬出。

### 3.2 Python 控制面

- 协议：同 UID Unix socket，单行 JSON，8 MiB，16 并发，10 s 读写超时。**无 per-op 版本**，只有 `service.status` 返回 `protocol_version: 1`；参数集合精确匹配，多一个 key 即 `invalid_request`。
- 错误：扁平字符串码，**任何非五大异常族的异常都变成 `invalid_request`**（control.py:622-623）；`CredentialManager._submit` 把非 CredentialError 一律变 `configuration_operation_failed`；`Pipeline._step` 把 Evidence/Editorial/Provider/Runner 错误折成 `blocked/preparation_failed`，原因丢失。
- 长任务两套模式并存：部分用 `request_id` + `*.status` 轮询，`sources.discover/preview`、`bots.verify`、`x.accounts.add` 阻塞连接且**无服务端超时**。
- **≥6 套独立 revision**（config / schedule / budget / media / newspaper / x.video / x.alerts），冲突码各异。probe / bot registry / X verify 直接写 `app_configuration`，**在 UI 背后 bump config revision**。
- **没有「我还差什么」的聚合调用**。UI 要凑齐 service.status + config.get + bots.list + credentials.status(×N Keychain) + models.status(×N) + route.preview(×N) + schedule.status + budget.get + sources.list。
- `_dispatch` 275 行 if 链；`ControlServer.__init__` 接 25 个协作者；`Operations` 直取 `store._db / _write / _save_config_tx`，跨 6 个模块 import 私有常量；credential lock 实际是全局写互斥，未文档化。
- 58 张表、25 个 `initialize()`，只有 `app_configuration` 有版本化变换；其余 `CREATE IF NOT EXISTS`，`DATABASE_VERSION=23` 实际只表示「哪些表存在」。备份校验返回 `restorable: False`。
- 状态词汇不统一：job 有 `stage`+`status`，occurrence 有 `status`+`reason`，delivery 有 part / target / reason 三层；`blocked` 在四张表里含义不同；`paused` 是 job 位、bot 位、也是 target reason。
- **两套产品并存**：`bot.py` / `config.py` / `schedule.py` / `service.py` / `store.settings|deliveries_v2|collections|briefs` 是 `.env` 时代的单 Bot 原型，仍可通过 `cli run / service install` 触达；`_LEGACY_SCHEMA` 每个新库都会建。`news.py` 同时被核心引用（`source_manager.py:26-34`）——需先拆出 `newsparse.py` 才能删旧栈。
- 密钥：Telegram token 在 URL path 里，靠 httpx logger 上的正则过滤器兜底（telegram/client.py:24-44），脆弱。
- 定价：`budget.default_policy().openai_credit.amount = 100_000_000` 且 `verified: False`，`budget.get` 把它当真值返回。X `daily_limit` 默认 `None` = 不限。

### 3.3 领域模块

- 源：web 适配器只覆盖固定站点表（`connectors/web.py:227-228`）+ 一个 AV 源；其余全是禁用草稿。推荐目录 `availability` 永远 `not_verified`，`dated_observation` 是静态字符串——**UI 不能把它当实时健康渲染**。
- 模型：运行时熔断状态（`model_health`）**没有任何控制操作暴露**（只在支持快照里）。
- 校验：后端错误码只够做 toast，**字段级校验必须在 Swift 端复刻 `app_config.py` 规则**。
- 重复：17 个模块各自定义 `_json`，37 份 `_json/_now/_clock/_time/_id` 拷贝；5 个同名 `*_scopes()`。
- 五处独立时区（全局 / 订阅 / budget.model / budget.x / alerts / video）无继承。
- 测试：49 个文件 15.8k 行，覆盖面好；`telegram/commands.py`（312 vs 1029 行）、`x/alerts.py`、`x/video.py` 相对薄；`source_catalog.py`、`media/image_provider.py`、`media/speech_provider.py`、`telegram/text.py` 无直接测试；遗留模块仍占 ~1.2k 行测试。


33 个失败集中在 `test_x_timelines`（17）/ `test_x_digests`（8）/ `test_x_alerts`（4）/ `test_x_video`（4）。已核实 `tests/test_x_timelines.py:13` 写死 `NOW = datetime(2026, 11, 8, …)`，而 fixture 里 `x.add_account/verify` 用真实时钟开了 11-09 的预算周期，之后 11-08 的预留触发 `clock_before_current_period` → `budget_blocked`。**高概率是测试时钟炸弹，不是产品回归**；确认方法是把时钟也注入 `XDirectory` 后重跑。

## 4. 重构建议（按依赖分层）

### 层 1 · 产品收敛（先冻结，再改代码）

1. **一个「简报」对象**替代 category + subscription + scope + route + target；字段：开关、时间[]、时区（默认系统）、bot[]、来源[]、条数、样式、国内/娱乐比例；拆分是显式动作。
2. **单一预算模型**：每月上限 $N（可空）+ 实际用量；内置 hold 常量；未知价格 → 标注不阻塞。
3. **调度跟随订阅**：首个简报开启即进计划；「暂停全部推送」一个开关。
4. **Key 保存即探测**（文字能力，约 $0.001，首次问一句）；其它能力在开启对应功能时探测；隐藏 TTS。
5. **单 Bot 自动成为普通目标**；成人目标仍显式。
6. **X 账号只有一个选项**：单独发 / 并入汇总。
7. 旧栈隔离：拆出 `newsparse.py`，删或移出 `bot.py / config.py / schedule.py / service.py / grok.py / ai.py` 与 `_LEGACY_SCHEMA`。
8. 更新 spec 19 / 21 / 29 / 33 / 35 / 40 的冻结契约（它们目前明文禁止重设计和默认值），以及 `docs/mockup/README.md` 基线。

### 层 2 · 后端配合（小改动，大杠杆）

1. 新增 **`setup.readiness`**：返回有序 `[{step, state, blocker_code, entity_id, fix_op}]`，输入已有（`routing.resolve_route`、`TargetManager.preview`、`ProfileRegistry.status`、`Scheduler.policy`、`BudgetLedger.policy`）。首页清单和「去处理」按钮都靠它。
